## 签约体检工单 bug：台账实体 ID 误当章节号（2026-11-01，fix commit 4c87ef37，已推 origin/master 0 0 同步）

用户反馈：某书仅写 7 章，但工单「涉及章节」出现第 1643 章、第 1653 章等上千编号；截图显示工单正文以 `reader_perspective`/`timeline` 标签开头、内含大量 `#编号` 引用，章节与分类标签混排。

根因链路：
- 系统约定台账实体引用写法为 `<type>#<id>`（如 `timeline#42`、`reader_perspective#1643`，id 为台账表自增主键，常达上千量级），放在 issue `desc` 里；台账类 issue 按合约 `chapter_ids` 应填 `[]`。
- `issueChapterIDs`（issue.go:103）优先吃结构化 `chapter_ids`，为空才回退 `parseChapterRefs(area,desc)`。
- `parseChapterRefs`（service.go:2384）的兜底正则 **`chapterHashRe` 原是裸 `#\s*(\d+)`**，把 `#1643` 这类台账引用当章节号抽出 → 工单 `chapter_ids` 列落脏值 → 前端 `chaptersOf`（IssueTicketsPanel.tsx:51）把数字渲染成「第N章」。同一工单同时出现真实章（第7章，来自 `第7章`）与台账 ID（第1643章，来自 `#1643`）这种混排，正是兜底正则同时抓到两类匹配的铁证（说明 `chapter_ids` 为空、走了兜底）。
- 连带隐患：`RewriteItem.Chapters`（S3 重写回流作用域）在 service.go:1344/1373/2323/2346、issue_tickets.go:467 等全部经 `issueChapterIDs` 填充——同一 bug 会把台账 ID 漏进「去重写第 1643 章」，是更严重的潜在错误重写。

修复（commit 4c87ef37）：
- `chapterHashRe` 收窄为 `(?:章节|章)\s*#\s*(\d+)`：只认「章#N」（漂移/文风类 issue 的 area 形如「章节#12」），台账 `<type>#<id>` 不再被误判为章节。
- 新增 `internal/pipeline/parse_chapter_refs_test.go` 锁行为：台账引用→不产出章节、章节+台账混排→只取真实章节、章节#N 仍正确解析。
- 单点修复同时堵住工单显示与重写回流两处台账 ID 泄漏。

存量数据说明：前端读的是工单行**已落库**的 `chapter_ids` 字段，此前那轮体检生成的脏行仍在库里。代码修复只防「下次」体检再生；该书当前视图要立刻干净，需对那本书**重新跑一次签约体检**（ReplaceIssues 会整批重建工单行，按修正后解析重新计算 chapter_ids）。台账引用本身仍保留在 issue `desc` 文本里，信息不丢，只是不再污染「涉及章节」。
