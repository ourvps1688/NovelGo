## 一致性巡检根因重构——后端批量取语料注入（消除 context deadline exceeded）
- 现象：巡检报告出不来，报错 `skill "consistency-patrol" 执行失败：context deadline exceeded`，张力清单正常。
- 根因（设计缺陷，非单纯超时）：旧 skill 让 LLM 自己用 `read` 工具逐章读全文（约 43 章 + 全部 17 张台账），
  单轮 50+ 次工具往返，60min 检测硬超时内跑不完；且全程无进度，前端只看到死转圈。
- 方案（用户选定「后端喂入正文」）：把语料预取从 LLM 移到后端。
  - 新增 `internal/pipeline/patrol_corpus.go`：`buildPatrolCorpus` 服务端批量读章正文（每章 cap 4000 字符、总预算 200000）
    + `dumpLedgers` 快照 17 张台账（每表 ≤300 行、总预算 60000），拼成 `【本书语料（后端已批量取...）】` 注入 prompt；
    `chapterStore`/`chapterTextReader` 为 nil 时优雅降级不 panic。
  - `patrol.go`：dispatch 前先 `buildPatrolCorpus` 注入，并 emit `pipeline:patrol_progress` phase=analyzing。
  - `events.go`+`service.go`：新增 `EvPatrolProgress` 事件与 emit 包装。
  - `consistency-patrol.md`：明确告诉 agent 语料已预取，禁止逐章 `read`（仅截断处可定向抽查）。
  - 前端：`PatrolReportPanel` 监听 `pipeline:patrol_progress`，渲染「读取正文 N/M…」/「语料已就绪，LLM 分析中…」替代死转圈；
    `zh-CN.json`/`en.json` 新增 `patrol.progress` 文案；`DetectionCorePanel`/`DetectionWorkflowView` 透传 `novelId`。
- 验证：后端 gofmt/build/vet/golangci-lint(webkit2_41,0 issues)/go test(全绿 118s)；前端 format:check/i18n:check/lint(0 err)/build 全过。

## 巡检·结构仍失败＝供应商流不完成（非设计缺陷）+ fail-fast 兜底
- 用户重启 dev 后再跑巡检·结构仍报 `context deadline exceeded`（novel 19）。调研确认：运行实例二进制 17:58 构建 > 提交，修复已加载；
  失败根因是 LLM 供应商「连得通但吐字节后掉线/极慢」，日志 `novelgo-llm.log` 整日被 `idle watchdog fired, canceling request idle=9mXs` 刷屏，
  主日志 `patrol.go:74` 18:59 落 `context deadline exceeded`，穿插 `持久化 usage 失败` 证明供应商吐了 token 后挂起。
- 设计层无问题：巡检始终按 novelID 收敛（runConsistencyPatrol→SkillInput.NovelID→tc.NovelID；全部 get_*/read 工具均 WHERE novel_id）；
  旧「逐章读全文」与本次「后端批量注入」都只碰当前书，不存在读全库。
- fail-fast 兜底（两处）：
  - `internal/pipeline/patrol.go`：新增 `patrolHardTimeout=20min`，给单次巡检调用 `context.WithTimeout` 派生 deadline（替代结构路径 60min）；
    新增 `classifyPatrolFailure` 区分 `idle_timeout`/DeadlineExceeded（清晰「供应商无响应/半死连接」提示）与通用错误，不再把原始 deadline 原文甩给用户。
  - `internal/agent/agent.go`：流错误处理把「流式吐字节后中断（StatusCode=0 + responseBuffer 有内容，即连接重置/EOF 掉线）」也计入
    `idleTimeouts` 快速放弃计数，堵住 `idleRetryCap` 此前只认 clean idle_timeout、漏掉 EOF/重置分支导致一路重试到 60min 的缺陷。
