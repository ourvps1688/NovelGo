## create_character 参数格式不正确 bug 修复（Q1 结案）
- 用户口述截图提示：「参数格式不正确: json cannot unmarshal array into Go
  struct field CreateCharacterArgs.characters.0.abilities of type string」
  ——非正常提示，是真 bug。根因：abilities/personality/detail_json/tags/
  params 等字段 Go 侧声明 string（存 JSON 文本），工具描述却教 LLM 传
  JSON 数组/对象；Registry.Execute 严格反序列化直接炸。update 工具的
  tc.RawArgs PATCH 二次解码（→ DB entity string 字段）是同类第二炸点。
- 修复（commit 8add66ac）：**中心化宽容化** args_coerce.go——在唯一反序列化
  入口 Registry.Execute 按 Args 结构递归把 string 字段收到的数组/对象值就地
  规范化为紧凑 JSON 文本，两条解码路径同时修复（否决逐字段自定义类型方案：
  覆盖不了 PATCH 路径且要动 schemaof $ref 兄弟键合并）。纪律：字符串原文/
  null 原样；数值/布尔进 string 仍报错（真类型错误）；json.Number 透传防
  大整数精度损失；无可改写返回原始字节（不动 key 序）。DisallowUnknownFields
  不变。schema 描述统一改为「数组/对象或字符串形式 JSON 文本均可」；
  rules.md §9 + AGENTS.md 记 tc.RawArgs 已规范化。
- 测试：coerceJSONTextArgs 单测 + 回归 TestCreateCharacterAcceptsJSONArray-
  AndObject（复现原始报错载荷）+ update PATCH/地点 tags/不变量 params/未知
  字段仍拒。mcp_tools 全绿 + lint 0 issue + 全量 go test 绿（TestRewriteVoiceABE2E
  全量并行下偶发红、单跑 66s 过，是 LLM E2E 资源抖动，与本改动无关）。
- 坑：golangci-lint govet 禁用 deprecated 别名 reflect.Ptr，须用 reflect.Pointer。

## 复验二次提速（round 2，commit 7cb6f485，已推送 0 0）
- 用户反馈「单条复验仍极慢」，DB 实据：I7 单批烧满 25min 预算未出回执、I5 verifying 7min+。根因=预算/提示词残留而非架构：旧 24k tokens×3 轮≈72k 思维预算（50tok/s≈24min）+ 提示词教「用 get_* 取数」与语料块禁工具自相矛盾致首轮工具调用空转 + 工具真暴露。
- 修复三点（勿回退）：①预算对齐体量：verifyTicketTimeout 25→15min、verifyMaxTurns 3→2、verifyMaxTokens 24k→10k（回执~300tok，10k≈20x 余量）；②**工具零暴露**：verifyBatch 派发 `Whitelist: []string{}`（skillrun.go 中 SkillInput.Whitelist 非 nil 即覆盖默认 allowlist）→ OpenAI 不给任何 tool schema，调用结构性不可能，单轮必出回执；③提示词去工具教学：verifyPrompt/ledgerChangeVerifyBlock 删「用 get_* 读台账/按 chapters 读段落」，改「直接通读语料」，加「输出从简≤3 句」。
- 新增 TestVerifyBatchZeroToolsAndLeanPrompt 断言 Whitelist 空集+MaxTurns≤2+MaxTokens≤10k+提示词无工具教学。
- **扩容答复（用户问百万字会不会更慢）**：不会。语料硬帽 verifyChapterCap 8k/verifyLedgerCap 8k/verifyCorpusCap 40k 字符，单次复验输入体量与书长无关——100 万字小说单次复验输入≈10 章小说同级。慢是预算/提示词债，非架构问题；批量合验+语料内联架构保持。
- 预期效果：单条复验典型 1-3min，异常批 15min 收口（原 25min+ 可能烧满）。在途 verifying 工单被热重建启动清扫自动复位 pending。
