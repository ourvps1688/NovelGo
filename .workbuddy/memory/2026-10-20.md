## S5 修复卡死排查 + 修复进度可视化（2026-10-20，commit 待推送）
- **卡死根因（本地日志实锤）**：用户报 S5「按体检问题修复中」永久转圈、日志无新输出。日志链：09:48:01 fix agent `edit` 第24章成功 → 09:48:08（6s debounce）edit 自动触发的 statesync 子 agent 后台同步，09:49:22 输出摘要后正常结束；**此后父 fix agent 09:48:08 发起的下一次 LLM 流式调用再无任何事件**（无报错/无 usage/无阶段流转），卡死 12+ 分钟。根因：`internal/llm/stream.go` HTTP client `Client.Timeout=0`、`ResponseHeaderTimeout=10m` 只管首字节，**SSE body 读取无 chunk 间空闲超时**——流静默断开（服务端挂起/网络静默丢流）时 `streamLoop <-stream` 永久阻塞，且 pipeline 用 `s.appCtx` 永不取消。
- **修复（LLM 空闲 watchdog）**：`stream.go` 加 `streamIdleTimeout=3min` + `idleWatchdog`（轮询 lastActivity，超时 cancel 派生 `streamCtx`）+ `kickReader`（读到字节即刷新）+ `idleTimeoutError`（`parseSSE` scanner.Err 识别后发可读的 retryable EventError → 走既有 P2 自动重试）。`resp.Body` 在 defer Close 之后替换为包装 reader（defer 捕获的是原 receiver，原 body 仍被关闭）。`generate.go` 非流式路径同样加 watchdog。`parseSSE` 签名不变（靠替换 resp.Body）。
- **修复进度可视化**：`agent.RunOptions` 加 `EventPrefix`（默认 "agent:" 不影响主聊天；RunSubAgent 透传）；`pipeline/skillrun.go` 设 `EventPrefix: "pipeline-agent:"` → 前端监听 `pipeline-agent:1` 拿工具事件（display_text/phase/success）做实时活动流。`events.go` 加 `EvFixStart`/`EvFixDone` + `FixIssuePayload`；`service.go executeFix` 开工时解析 ContextJSON.Audit issues 广播修复清单（问题+涉及元素），结束广播 ok/error。前端：`usePipeline` 监听三事件维护 `fixProgress`/`fixActivity`（只记 completed/failed 终态，cap 40）；`SignabilityAuditView` 新增 `FixProgressView`（spinner + 修复清单 + 实时动态 + 完成待复评/失败文案）；`PipelineWizard` 透传 props；i18n 加 `pipeline.fixProgress.*`。
- 教训：**i18n JSON 不能用 python json.dump 整文件重写**（会把内联数组展开成多行产生巨量 diff），必须用 Edit 工具定点插入。

## S5「假修复完成」+ 僵尸运行排查（2026-10-20 第二轮，commit 待推送）
- **现象**：应用重启后界面停在「修复完成，正在自动复评……」，10:50:26 用户点一键连跑（DB 仅 auto_run=1 更新）后再无任何后端活动，日志只有 activity_daily 心跳。
- **诊断（两个叠加问题）**：
  1. **设计缺口（主因）——僵尸运行**：pipeline 执行体是内存 goroutine + DB 状态，应用重启（10:10、10:49 两次）后 goroutine 消亡但 DB 仍 S5/running，无任何启动恢复机制。`set_auto`/`resume` 都只改 DB 标志不派发执行体 → run 永久空转。
  2. **前端假象**：`FixProgressView` 初始态 `{running:false, ok:null}` 恰好命中 done 分支渲染（`running??true` 也错了——初始 fixProgress 是定义过的对象不会 undefined），重启后直接显示「修复完成待复评」。
- **修复**：
  - `store.go`：`GateContext.Interrupted` 标记 + `ListByStatus`。
  - `service.go`：`RecoverInterruptedRuns()`（OnStartup 调用：running→paused+打标记，幂等）；`redispatchInterrupted()`（resume 时按阶段重派发：S4/S4b→executeAudit、S5→executeFix、S6→executeFinalAudit，派发后清标记；executeAudit/executeFix/executeFinalAudit 均幂等重入有守卫）。
  - `app/handler.go`：初始化 pipeline 后调 `RecoverInterruptedRuns()`。
  - 前端 `FixProgressView`：初始态按 idle 渲染（Hourglass + 「等待修复启动……」），隐藏 reAuditing 与活动区；i18n 加 `fixProgress.idle`。
  - 新测试 `TestServiceRecoverInterruptedAndResume`：僵尸→恢复暂停→resume 重派发→回 S4 闸门 + 清标记。
- 教训：**Edit 工具 old_string 带结尾换行而 new_string 不带会把下一行拼上来**，编辑后要回看。

## S5 分批修复 + 失败状态落地（2026-10-20 第三轮，commit 待推送）
- **用户问题**：S5 显示「修复失败：已达最大轮数，对话结束」卡死；7 个复杂问题（整章改写/重排/合并台账）一轮对话 12 turns 根本吃不下；且失败后停在 S5/running 无任何恢复出口。
- **修复设计（两层）**：
  1. **分批修复**：`planFixBatches` P0 每批 1 条、P1 每批 2 条，每批独立 skillRunner 会话（`pipeline:<runID>:fix:<uuid>`，防历史挤占轮数）+ 独立 12 turns 预算；`fixPrompt` 只传本批问题子集。每批成功即落 `GateContext.FixStates[issueID]="fixed"` 断点（失败恢复/重启续修跳过已修项）；全部完成走 `finishFixAndReaudit`（FixRounds++ → 复位体检阶段 → 复评，复评才是「修复到位」的最终裁决）。
  2. **失败不再卡死**：executeFix/executeAudit/executeFinalAudit 失败一律落 paused + note（原来停 running 无出口）；新增 `GateContext.Dispatching` 标记（执行体派发/退出时维护），resume 据此区分软暂停（执行体仍在，批次边界守卫感知恢复）与无人执行（重派发）；`redispatchInterrupted` → `redispatchIfNeeded`（不再要求 Interrupted 标记）；RecoverInterruptedRuns 启动时清失真 Dispatching。批次间守卫：用户暂停/中止在批次边界生效。
- 前端：fix_start 增加 batch_index/batch_total/done_ids；FixProgressView 显示批次进度、「已修复 N 项」徽章、失败时 resumeHint；i18n 新键 batch/fixedCount/resumeHint。
