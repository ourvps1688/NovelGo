## ONNX 使用调研与增益评估（仅调研，未改代码，用户拍板暂不动）
- 用户问题：本项目采用了 ONNX 的相关设计，查看代码具体哪些地方用到了；评估还有哪些地方可增益、增强后收益。
- 调研结论：ONNX Runtime 在本项目**只做文本向量化**——单一模型 `bge-small-zh-v1.5`（int8，512维），经 `internal/rag/embedder_onnx.go` 的 `OnnxEmbedder` 单例（异步加载、`e.mu` 串行 Run、CLS+L2、批量≤8、arena 治理、`Compact` shrink）产出 embedding，写入 `vec0`/`sqlite-vec` 向量库。`ort` 导入仅此一处；第三方 `third_party/onnxruntime_go` 是 vendor 的 Go 绑定（yalue/onnxruntime_go v1.30.1 + patch），`scripts/download-onnx.sh` 下载 ORT v1.26.0 动态库 + BGE 模型，`internal/platform/runtime.go:ResolveOnnxLib` 定位动态库。手写 BERT WordPiece tokenizer（`tokenizer.go`）不依赖 ORT。
- 4 个消费方（全部 `if vs==nil` 优雅降级）：①章节语义检索 `IndexChunks`/`Search`；②设定语义检索 `setting/index_search.go:SearchSettings`（无 ONNX 退化为 LIKE）；③模式抽取证据前置 V2-D `app/pattern_api.go` 的 `ragEvidenceRetriever`；④故事记忆语义召回 MCP `mcp_tools/memory_tools.go`（已用 `rag.MMRRerank` 纯 Go 多样性重排，非模型）。
- 缺口：无 rerank 模型（top-K 仅 cosine+MMR 粗排）；端侧算力仅用向量化；512 截断+CLS pooling 长文漏召；V2-D 多查询串行未批处理/未缓存；机械类判定与实体抽取仍靠规则/LLM。
- 增益候选（按性价比，已写入 MEMORY.md ONNX 节）：P0=二阶段 reranker（bge-reranker-v2-m3 int8）+检索批处理/短 TTL 缓存；P1=长文分段聚合/升级 embedding 模型；P2=本地分类器/NER 替代部分 LLM 判定（离线零隐私外传，契合隐私红线）；P3=端侧生成式续写（ORT 对 decoder-only 支持弱，短期不推荐）。动手前须评估低端机内存 + 更新 `download-onnx.sh`。
