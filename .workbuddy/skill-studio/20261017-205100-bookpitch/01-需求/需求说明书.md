# Phase 1 · 需求说明书 — book-pitch 重做（NovelGo 内置 skill + 前端 v2）

> 流水线形态：专家五阶段（构思→设计→实现→测试→打包）在 **NovelGo 语境**下执行。
> 该专家的 WorkBuddy 专用工具（contract.yaml / validate_skill.py / package_skill.py）不适用，门禁改用 `tsc` / `prettier` / `i18n:check` / `theme:check` / `eslint` / `vite build` 与 JSON 契约一致性自检。

## 0. 形态与边界（本阶段必须定清，否则下游返工）
- **交付形态**：NovelGo 应用内置 skill，文件 `internal/skill/builtin/book-pitch.md`，经 `internal/skill/builtin.go` 的 `//go:embed builtin/*.md` 嵌入，运行时随 Go 重编生效。
- **不是**独立 WorkBuddy agent skill 包；不脱离 NovelGo，保留与前端「终稿 JSON 自动回填书架」的集成。
- **范围**：book-pitch.md 文案重构 **+** 前端解析/自动保存逻辑升到 **v2**。

## 1. 目标用户
- NovelGo 用户，处于「开新书」阶段，需要一个专业、可签约导向的外包装（书名 / 200 字钩子简介 / 标签 / 方向 / 题材 / 平台 / 风格 / 一句话卖点）。
- 用户可能是网文新手，也可能是老手；skill 须同时给出「方法论」与「可直接采用的成品」。

## 2. 核心能力
1. **签约向外包装方法论**：分平台书名公式、200 字钩子简介结构、标签选型、一句话卖点电梯演讲、自检清单（诊断式）。
2. **对话式打磨**：与用户在 chat 中迭代讨论，逐步收敛到可签约外包装。
3. **终稿结构化输出**：定稿时在回复末尾输出严格 schema 的 JSON（围栏语言标记 `bookpitch`），供前端解析。
4. **（前端 v2）字段级增量回填**：解析到 JSON 后，回填表单并自动保存书架；用户手动改过的字段受保护不被覆盖，提供冲突提示与「采用全部建议」入口。

## 3. 触发场景
- 书架顶部「AI 孵化新书」入口 → 进入 bookpitch 顶层面板 → 输入灵感 → 开始 → 与 book-pitch 对话 → 终稿 JSON 自动回填并保存书架。
- `mode: manual`，由启用注入 system 上下文，用户在孵化流程中调用。

## 4. 边界（明确不做什么）
- **只产出外包装文案**，不动正文；正文由 opening-chapters / story-blueprint 等负责。
- 不替代 `signability-audit` 的联合体检，仅在外包装维度自检，并提示用户后续触发 signability-audit。
- 终稿 JSON 仅作前端回填载体，不得夹带与 8 字段无关内容。

## 5. 验收标准（可检验）
- [ ] book-pitch.md 含完整方法论章节（书名分平台 / 200 字钩子 / 标签 / 卖点 / 自检 / 签约向），且「终稿结构化输出」章节 schema 与前端解析字段**逐字段对齐**。
- [ ] 前端 v2 能正确解析该书稿 JSON，8 字段全部回填；书名/简介/题材写回小说主体，其余写入本书偏好。
- [ ] 用户手动修改某字段后，后续 JSON 更新**不覆盖**该字段；冲突时给出提示。
- [ ] 提供「采用全部建议」按钮可强制以最新 JSON 覆盖全部字段。
- [ ] 聊天 UI 不显示 ```bookpitch 机器块。
- [ ] `tsc`/`prettier`/`i18n:check`/`theme:check`/`eslint`(0 error)/`vite build` 全过。
- [ ] 改动提交并推送到 `origin/master`。

## 6. 平台 / 通道 / 交付物形态三参数（专家 SOP 要求）
- 平台：NovelGo（非 workbuddy）；通道：local（内嵌于 NovelGo 仓库）；形态：NovelGo 内置 skill（markdown + go:embed）。
- 注：此三参数偏离专家的 WorkBuddy 默认值，已在本说明书明确，下游以本说明书为准。
