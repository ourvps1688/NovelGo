## 2. SKILL.md frontmatter 设计

> 字段集合与形态以 NovelGo 内置技能格式为准（参考 `internal/skill/builtin/next.md`、`story-blueprint.md` 等真实文件）：`name` / `description` / `category` / `mode` / `author` / `version` / `useWhen`（数组，每项 `{intent, cues:[...]}`）。无多余字段。

```yaml
---
name: signability-workflow

description: 签约潜力工作流——把 story-blueprint、worldbuilding-design、signability-audit 三个内置技能编排成「现状诊断→规划蓝图→世界设定→写作推进→签约体检→闭环回修」的引导式闭环，当用户以冲击平台签约为目标、需要通盘规划与体检时手动触发。

category: 系统

mode: manual

author: builtin

version: 1

useWhen:
  - intent: "规划签约潜力 / 通盘编排签约工作流（规划→设定→写作→体检→回修）"
    cues:
      - "签约潜力"
      - "签约规划"
      - "签约工作流"
      - "一书通盘规划"
      - "蓝图到体检"
      - "过签规划"
      - "帮我规划签约"
      - "这本书能不能签"
      - "编辑愿意签吗"
      - "签约潜力工作流"
---
```

### 2.1 字段取值论证

| 字段 | 取值 | 论证 |
|------|------|------|
| `name` | `signability-workflow` | 与需求 §9 决策一致（新建而非复用 `next.md`）；文件名须同名（见 §1.3）。 |
| `description` | 一句话含触发语义 | 单句陈述「编排对象 + 6 阶段骨架 + 触发条件」；触发语义（"以冲击平台签约为目标、需要通盘规划与体检时手动触发"）直接写入，利于技能矩阵发现与 `mode=manual` 下的用户意图匹配。 |
| `category` | **`系统`**（主理人锁定） | **论证（主理人裁定，替代原"流程"建议）**：经核查现有内置技能分类（包装/创作/角色/系统/技法/开篇/结构/情节/读者/修订/评估/设定），**没有"流程"这一分类**；而 `next.md`/`collect.md`/`memory.md`/`review.md` 等**调度/元技能**统一归在 `系统`。本技能本质是编排总调度（orchestrator），与 `next.md`（同为总调度）性质最相近，故归入 `系统` 既与现有 taxonomy 一致、又明确它是"元/调度"而非某个创作职能（避免与叶子技能 `结构`/`设定`/`评估` 混淆）。原"流程"建议会凭空新增一个目录分组，已废弃；"签约"亦可作主题聚合备选，但 `系统` 更贴切且零新增分组。 |
| `mode` | **`manual`**（确认） | **论证**：① 需求 §3.1 推荐 `manual`；② 门禁 §12.5 已锁定 `manual`；③ 本技能是一条**长流程引导**，若 `mode=auto` 会在每次聊天都被加载一长段编排提示，干扰其它技能（尤其与同样会调 signability-audit 的 `next.md` 冲突）；④ 用户需有"进入工作流"的明确意图才触发，与收窄的 `useWhen` cues 配合最稳；⑤ 与同为总调度的 `next.md`（`mode: manual`）保持模式一致，降低用户认知成本。 |
| `author` | `builtin` | 内置技能统一署名（与全部现有 builtin 一致）。 |
| `version` | `1` | 首次新建，初版为 1（与 `story-blueprint`/`worldbuilding-design`/`signability-audit` 新建初版口径一致）。 |
| `useWhen` | 1 个 `intent` + 收窄 `cues` | `intent` 概括"规划签约潜力/通盘编排签约工作流"；`cues` 以主理人建议的 7 个关键词（签约潜力/签约规划/签约工作流/一书通盘规划/蓝图到体检/过签规划/帮我规划签约）为基线，并补充需求 §3.1 的两条真实触发语（"这本书能不能签""编辑愿意签吗"）与技能自指词（"签约潜力工作流"），共 10 个，既收窄又覆盖典型表达，避免误触发单点技能（见 B1 不抢夺）。 |

## 3. SKILL.md 正文大纲（骨架，非全文）

> 原则：正文是给 LLM 的**技能指令**。被编排技能**只引用技能名**、由 LLM 经技能目录 `read` 加载（auto 技能按需读、manual 的 signability-audit 由本工作流显式触发），**严禁重写**其方法论与落库逻辑（B1/B5）。

### 3.1 标题层级骨架

```
# 签约潜力工作流（Signability Workflow）          ← 角色声明：你是"签约潜力总导演"
## 何时使用（手动）                                ← 复述 useWhen 触发语义 + 不介入清单（B1/B7 边界）
## 对齐声明（全局铁律）                            ← 题材卡优先级、只编排不落库、不臆造、不越权
## 阶段总览（给用户的第一屏）                      ← 6 阶段清单 + 每阶段目标/完成判据/调用技能名/题材卡提示（满足 AC1）
## 阶段 0：现状诊断（数据读取闸门）                ← 真实读取本书数据，决定后续从哪进（C3/AC2/AC9）
## 阶段 ①：规划蓝图                               ← 调 story-blueprint
## 阶段 ②：世界设定                               ← 调 worldbuilding-design（按需）
## 阶段 ③：写作推进                               ← 引导写作 + 可选调 next（下一章总调度）
## 阶段 ④：签约体检                               ← 调 signability-audit
## 阶段 ⑤：闭环回修                               ← 把 P0/P1 映射回阶段+技能（C4）
## 阶段间分支逻辑（依据真实数据）                  ← 引用 §12.4 口径，决定跳过/合并/复检/补充
## 每阶段收尾模板（C6 结构化产物清单）             ← 本阶段产物 + 下一阶段触发词 + 调用技能
## 工具协同清单                                    ← 本技能直接调用的读取/编排工具（不含落库写指令）
```

### 3.2 各节要点（可实现的骨架）

- **角色声明**：你是"签约潜力总导演"，职责是**编排** `story-blueprint` / `worldbuilding-design` / `signability-audit`（及可选 `next`）按序推进，不替代任何专项技能的业务逻辑。
- **何时使用 / 不介入**（对齐需求 §3.2、边界 B1/B7/B8）：用户表达签约目标意图（cues 命中）时进入；用户只问单点（"帮我设计世界观"→直接走 worldbuilding-design）、已在某阶段且未表进入意图、非签约写作、非 NovelGo 项目 → 不抢夺、不介入。
- **对齐声明（铁律）**：
  - 题材卡（genreTemplates）优先级 > 任何专项技能通用教义；全程引用注入的 genre 约束（开场抓手/冲突发动机/章尾钩子/禁止漂移/爽点密度/情绪曲线/字数门槛）。
  - **只编排不落库**（B2）：正文不含 `create_story_arc` / `upsert_setting` / `create_location` / `update_chapter_plan` 等写指令；落库完全由被编排技能在其引导下的用户操作执行。
  - **不臆造**（B6/AC9）：任何阶段判定前必须先真实读取数据；读不到即兜底停止。
  - **不越权**（B7）：只呈现 signability-audit 的致命伤与建议，不替编辑/平台做一票否决。
- **阶段总览**（AC1）：以表格/清单列出 6 阶段，每阶段含【目标】【完成判据】【建议调用技能名】【题材卡约束提示】四要素。
- **阶段 0：现状诊断**（C3/AC2/AC9，核心闸门）：
  - 先用 `get_chapter_list` 取章节；若返回空或读不到 → 提示"无法读取本书数据，请确认在 NovelGo 项目中"并**停止**，不臆造（AC9）。
  - 依次真实读取：`get_story_arcs`（按 `arc_type=main` 判蓝图）、`search_settings`（判设定）、`get_reader_perspective`（判体检）。
  - 据读取结果生成"当前进度卡"，决定后续从哪一阶段切入（见 §6 / §3.2 分支逻辑）。
- **阶段 ①：规划蓝图**：引导调用 `story-blueprint`（auto，LLM `read` 加载）；说明调用时机、输入（本书立意/题材）、预期产出（卷纲/主线 arc/arc_node/chapter_plan）；提示题材卡「情绪曲线/爽点密度/章尾钩子」约束。完成判据=本书出现 ≥1 主线 arc + ≥1 arc_node 或更新卷纲（AC3）。
- **阶段 ②：世界设定**（按需）：引导调用 `worldbuilding-design`（auto）；说明何时需要（力量体系/金手指/地图势力）、输入、预期产出（`upsert_setting`/`create_location` 等落库，AC4）；提示题材卡「金手指一致性/禁止漂移」。若阶段 0 已检出设定库非空 → 提示"补充"而非从零（§6）。
- **阶段 ③：写作推进**：引导用户依蓝图+设定+题材卡约束动笔；**可选**调用 `next`（下一章创作总调度，auto）作为写章驱动（需求 §9.4 明确"不强制"）。本阶段只给写作方向与题材卡红线，不替写。
- **阶段 ④：签约体检**：引导调用 `signability-audit`（manual，本工作流显式触发）；说明输入（成稿章节）、预期产出（七维打分+致命伤+P0/P1 建议，经 `upsert_preference` 存"本书签约体检"，AC5）。若阶段 0 已检出 `get_reader_perspective` 非空 → 提示"复检"而非从零（§6）。
- **阶段 ⑤：闭环回修**（C4/AC6）：将体检 P0/P1 建议**逐条映射**到"回到哪个阶段 + 调用哪个技能"（如 P0=开篇无代入感→回阶段①重做黄金三章立意；P1=力量崩坏→回阶段②调 worldbuilding-design）；提示"修复→复检"回路。**不设计"读旧体检报告"步骤**（preference 无回读工具，§12.3 ⚠️），靠重新跑 audit 闭环。
- **阶段间分支逻辑**（见 §6 独立成节，C3 落地）。
- **每阶段收尾模板**（C6）：统一输出"本阶段产物清单 + 下一阶段触发词 + 调用哪个技能"，便于用户感知进度。
- **工具协同清单**：本技能直接调用的**读取/编排类**工具 —— `get_chapter_list` / `get_story_arcs` / `get_timeline` / `search_settings` / `get_reader_perspective` / `read` / `run_subagent(review)`；**明确声明不含任何落库写指令**（B2/AC8）。

## 4. LLM / 脚本分工矩阵

> 需求核心能力 C1–C6，**逐条过脚本化边界判定问句**（确定性 / 理解 / 失败三问），结论须与需求 §7 / §11.2 一致：**6 项全部由 LLM 提示词实现，不引入任何脚本或 references**。
> 判定问句定义：
> - **Q1 确定性**：给定相同输入，输出是否永远相同、可逐条枚举？
> - **Q2 理解**：任务是否需要理解用户意图、语义分类或自然表达匹配？
> - **Q3 失败**：失败模式是否可预测、可显式报错？

| 能力 | Q1 确定性 | Q2 理解 | Q3 失败 | 边界问句裁决 | 结论 | 理由 |
|------|-----------|---------|---------|--------------|------|------|
| **C1 阶段引导（主编排骨架）** | 否——引导语需依运行时真实数据（蓝图/设定/体检是否已做）动态组织，输出随数据变 | 是——需理解用户进度与意图决定引导措辞 | 否——用户中途改目标等失败不可枚举，需自然语言兜底 | 理解型为主，确定性仅限"阶段顺序"这一弱规则；不适合脚本 | **LLM 提示词** | 编排骨架是自然语言指令，硬逻辑（落库/评分）已在被编排技能内；阶段顺序规则简到可在提示词内 if/else 表达，无需脚本。 |
| **C2 技能调度（只编排不重写）** | 否——"何时调哪个技能/输入什么/预期产出"是交互式自然语言，输出不固定 | 是——需理解用户当前状态以生成调度指引 | 否——用户不跟随需自然语言追问，不可枚举 | 理解型，非确定性 | **LLM 提示词** | 调度本质是"告知用户下一步"，由 LLM 读真实数据后用语言描述；调用目标（技能名）是常量，但编排表达是提示词。 |
| **C3 阶段状态感知（防重复）** | **部分**——"get_story_arcs 非空→蓝图已做"是确定规则；但"综合多源给下一步指引"是自然语言 | 是——需理解读取结果并综合判断所处阶段 | **部分**——"读不到→AC9 停止"是确定性；"读到了但残缺"需模型判读 | **灰区裁决：拆分**——"是否非空"判定由工具返回直接决定（LLM 内 if 分支即可，无需独立脚本）；"综合判断+生成引导"留给 LLM | **LLM 提示词** | §12.4 已把状态判定口径固化为确定性条件（arc 非空→跳过规划；perspective 非空→复检；setting 返回→补充），这些条件在提示词内用工具调用+if 分支表达即可，**无需 Python 脚本**。无独立状态机脚本。 |
| **C4 闭环回修引导** | 否——"每条 P0/P1 映射到回哪阶段+调哪个技能"依赖对建议语义的理解，输出随建议内容变 | 是——需理解体检建议语义做映射 | 否——建议格式多样无法枚举，需模型判读 | 理解型，非确定性 | **LLM 提示词** | 映射是语义理解任务；映射表（建议类型→阶段/技能）可在提示词内给"示例→映射"骨架，但具体建议需 LLM 判读。 |
| **C5 题材卡约束遵循** | **部分**——genre 字段值是注入常量，引用本身确定；但"在引导语中显式提示约束"是自然语言编织 | 弱——主要是引用注入的 genre 约束 | **部分**——无题材卡时降级为通用标准（AC7），降级判断确定、不报错 | 引用型，确定性部分极薄，无需脚本 | **LLM 提示词** | 题材卡由系统上下文注入（§12.3 已确认，非工具），技能正文直接引用即可；无卡时按 AC7 降级提示不中断，全部可在提示词内表达。 |
| **C6 结构化产物清单输出** | 否——产物清单内容随该阶段实际产出变化 | 弱——模板化输出但内容动态 | 否——用户未产出需自然语言追问，不可枚举 | 模板+动态内容，非纯确定性 | **LLM 提示词** | "产物清单+下一阶段触发词+调用技能"是固定模板套动态内容，由 LLM 在每阶段收尾生成，无需脚本。 |

**汇总结论**：C1–C6 **全部由 LLM 提示词实现，引入 0 个脚本、0 个 references**。与需求 §7 / §11.2 完全一致。

**对 §11.2「可选增强」的核查**：需求曾列"若需程序化可靠阶段判定或跨体检 diff 再引入脚本/references"。经本设计核查：
- 程序化阶段判定 → 已由 §12.4 口径 + 现有读取工具（`get_story_arcs`/`search_settings`/`get_reader_perspective`）在 LLM 提示词内表达，无需脚本。
- 跨体检 diff → §12.3 标注为"可选、暂无工具"，不在本内核范围；且 C4 闭环靠重新跑 audit（§12.3 ⚠️ 设计约束），不依赖 diff。
- **故本设计不预留任何脚本/references 钩子**，维持纯单文件 `.md`。

## 6. 阶段状态判定逻辑（C3 落地，依据 §12.4 口径）

> 本逻辑是 C3「状态感知防重复」的可执行裁定。所有判定**前置条件=已真实读取**（AC2/AC9 铁律），禁止假设数据存在。

### 6.1 判定条件表（固化自 §12.4）

| 数据项 | 读取工具 | "已做"判定条件 | 分支行为 |
|--------|----------|----------------|----------|
| 蓝图 | `get_story_arcs` | 返回非空（尤其 `arc_type=main`） | 阶段 ① 规划：**跳过或合并**（不重复规划，满足 AC2） |
| 设定 | `search_settings` | 返回相关条目（语义命中本书设定） | 阶段 ② 设定：**提示"补充"**而非从零 |
| 体检 | `get_reader_perspective` | 返回非空 | 阶段 ④ 体检：**提示"复检"**而非从零 |
| 题材卡 | 系统上下文注入（非工具） | 注入存在 genre 约束 | 全程引用；不存在则 AC7 降级通用标准 |
| 签约体检偏好 | 无专用回读工具（仅 `upsert_preference` 写） | — | **不读旧报告**；C4 闭环靠重新跑 audit（§12.3 ⚠️ 设计约束，非阻塞） |

### 6.2 分支决策流（阶段 0 → 切入阶段）

```
阶段0 现状诊断:
  get_chapter_list 为空/读不到 → 提示"无法读取本书数据，请确认在 NovelGo 项目中"并 STOP (AC9)
  否则并行读取: get_story_arcs / search_settings / get_reader_perspective
  生成"当前进度卡":
    蓝图未做 → 从 阶段①规划 进入（主线推进）
    蓝图已做 & 设定未做 → 阶段①合并/跳过，从 阶段②设定 进入
    蓝图+设定已做 & 体检未做 → 从 阶段③写作/阶段④体检 进入
    体检已做 → 阶段④提示"复检"，并可直接进 阶段⑤闭环回修
  始终: 题材卡约束全程引用；无卡降级通用标准 (AC7)
```

### 6.3 防重复机制

- 已做阶段**不重新触发**其落库动作（如蓝图已做则不在阶段 ① 重复 `create_story_arc`），仅做"合并/补充/复检"提示（C3）。
- 每次进入工作流都**重新真实读取**（不缓存上一轮判断），避免基于陈旧假设重复触发（B6）。

## 7. 命名与字段合规

- **frontmatter 字段集合** = NovelGo 内置技能格式规定的 7 字段：`name` / `description` / `category` / `mode` / `author` / `version` / `useWhen`。
- **无多余字段**：未引入 `tags` / `tools` / `dependencies` 等任何扩展字段；与现有 `next.md`、`story-blueprint.md`、`signability-audit.md`、`worldbuilding-design.md` 的字段形态逐一对齐（上述文件实测均仅含这 7 字段）。
- **`useWhen` 形态**：数组，单元素含 `intent`（字符串）+ `cues`（字符串数组），与现有文件一致。
- **`name` 与文件名一致**：`name: signability-workflow` ↔ 落点文件 `signability-workflow.md`（§1.3），符合现有命名约定。
- **`mode` 取值合法**：`manual` ∈ {manual, auto, always}，合规。
- **正文合规**：单文件 `.md`，无 `scripts/`/`references/` 子目录（§11.2 免脚本/references）；正文为给 LLM 的指令，引用被编排技能名而非复制其正文（B1/B5）。
