# 需求说明书：签约潜力工作流（signability-workflow）技能内核

> 文档性质：需求说明书（本 run 的唯一事实来源，供下游设计 / 实现 / 测试 / 打包阶段直接使用）
> 关联 run：`20261016-135655-signflow`
> 编写角色：skill-ideator（技能产品负责人）
> 交付范围：**仅技能内核**（引导式编排技能 `.md`）；专属 UI 入口明确不在本次范围，后续单独做。

---

## 0. 一句话定位

把 NovelGo 现有的 3 个「签约」相关内置技能（`story-blueprint` / `worldbuilding-design` / `signability-audit`）**编排**成一个引导式的「签约潜力工作流」，引导用户按「规划 → 设定 → 写作 → 体检 → 闭环修复」推进，而非让用户零散打字触发单个技能。本技能**只编排、不重写**这 3 个技能。

---

## 1. 目标用户与痛点

### 1.1 目标用户
- 在 NovelGo（WorkBuddy 环境下的 AI 写小说应用）中创作、且**以「冲击平台签约」为目标的网文作者**。
- 已完成一定体量章节（≥3 章，几章到几十章不等），但不知道自己作品签约概率如何的作者。
- 缺乏结构化方法论、只会零散触发单个技能的作者是核心受众。
- 想把「先规划 → 再写 → 再体检 → 再修」做成闭环，但不清楚如何串联的作者。

### 1.2 痛点（即本技能要解决的 P2-3 问题）
1. **无引导闭环**：`story-blueprint` / `worldbuilding-design` / `signability-audit` 三个技能都能跑出真实报告，但用户只能靠聊天打字触发或在「技能矩阵」里发现，**没有引导式「签约潜力」工作流**把「规划蓝图 → 写作 → 签约体检」串成端到端闭环。
2. **不知何时用哪个**：用户完成一个技能后，不清楚「下一步该调用哪个技能、输入什么、预期产出什么」。
3. **数据不连贯、无回修回路**：蓝图、设定库、体检报告各自为政，缺乏「体检发现 P0/P1 问题 → 回到对应阶段调用相应技能修复」的回路。
4. **滞后模式**：用户常陷入「写完才体检」的滞后模式，错失早期规划窗口。
5. **无专属入口**：本次 UI 入口不做，但技能内核必须能独立承载引导，不依赖 UI。

## 2. 核心能力

本技能是「编排层 / 调度层」，核心能力如下（均不替代被编排技能自身的业务逻辑）：

- **C1 阶段引导（主编排骨架）**：以「①规划蓝图 → ②世界/设定（按需）→ ③写作推进 → ④签约体检 → ⑤闭环修复」为骨架，分阶段引导用户推进；每阶段明确**目标、完成判据、建议调用的现有技能名、以及题材卡约束提示**。
- **C2 技能调度（只编排不重写）**：在每个阶段提示并指导用户调用现有技能——规划阶段调用 `story-blueprint`、设定阶段调用 `worldbuilding-design`、体检阶段调用 `signability-audit`；说明调用时机、输入与公司预期产出；可借助 `run_subagent` 做交叉验证（如 `run_subagent(review)`）。
- **C3 阶段状态感知（防重复 / 给下一步）**：基于**实际读取的本书数据痕迹**（是否已有 story_arc / arc_node / chapter_plan、设定库、签约体检偏好）判断用户当前所处阶段，避免重复触发，并给出「下一步」可执行指引。判定前**必须先真实读取数据，禁止假设数据已存在**（见 §8、验收 AC2/AC9）。
- **C4 闭环回修引导**：体检产出 P0/P1 建议后，把每条建议映射到「回到哪个阶段 + 调用哪个技能」，并跟踪修复状态，形成「体检 → 修复 → 复检」回路。
- **C5 题材卡约束遵循**：工作流全程引导须服从本书「题材卡」(`genreTemplates`) 约束（开场抓手 / 冲突发动机 / 章尾钩子 / 禁止漂移 / 爽点密度 / 情绪曲线 / 字数门槛），在引导语中显式提示这些约束。无题材卡时降级为通用网文标准并提示，不中断。
- **C6 结构化产物清单输出**：每阶段结束时，向用户输出「本阶段产物清单 + 下一阶段触发词 + 调用哪个技能」的清晰小结，便于用户感知进度。

> 说明：C3 的「状态感知」由 LLM 在运行时经 NovelGo 读取工具获得真实数据后做判断，不需要独立脚本（见 §7）。

## 3. 触发场景

### 3.1 应介入（触发）
- 用户表达签约目标意图，例如：「帮我做签约潜力规划」「签约工作流」「让我的小说能签约」「怎么才能让编辑愿意签」「帮我评估一下这本书能不能签约」。
- 用户写完若干章后询问「接下来该做什么」且上下文指向签约目标。
- 用户在技能矩阵 / 聊天中主动要求进入「签约潜力工作流」。

**推荐触发模式（待设计阶段确认）**：`mode = manual`，并配置 `useWhen`（intent=签约潜力编排，cues 含「签约 / 潜力 / 编辑愿签 / 能不能签 / 工作流」等）。理由：这是一条长流程引导，应让用户**主动进入**，避免 `mode=auto` 在每次聊天都加载一长段编排提示而干扰其它技能。若下游更看重「技能矩阵可发现性」，可改为 `mode=auto` + `useWhen` 收窄 cues——此为设计阶段决策，本需求不锁定。

### 3.2 不应介入（不触发）
- 用户只问**单点**问题，如「帮我设计世界观」→ 直接走 `worldbuilding-design`，不必进入编排。
- 用户已在某阶段并产出结果、但未表达进入「工作流」意图时，不主动抢夺。
- 非签约类写作需求（纯娱乐草稿、无签约目标）。
- 当前项目非 NovelGo 项目、或读取不到本书数据（见 AC9）。

## 4. 边界（不做什么）

- **B1 不重写被编排技能**：不复制 `story-blueprint` / `worldbuilding-design` / `signability-audit` 的方法论文档与落库逻辑，只编排调用。
- **B2 不直接落库**：本技能正文**不包含** `create_story_arc` / `create_arc_node` / `upsert_setting` / `create_location` / `update_chapter_plan` 等直接写库指令；落库完全由被编排的现有技能（或其引导下的用户操作）执行。
- **B3 不替代评分逻辑**：不重做七维打分 / 致命伤清单 / P0·P1 建议——评分由 `signability-audit` 完成，本技能只负责引导触发与汇总呈现。
- **B4 不做 UI**：专属 UI 入口明确不在本次范围。
- **B5 不修改现有 3 个技能文件**：编排对象保持不变。
- **B6 不臆造数据**：不能假设本书已有蓝图 / 设定 / 体检结果，所有阶段判定必须基于实际读取结果（见 §8、AC2/AC9）。
- **B7 不做越权判定**：只呈现 `signability-audit` 的致命伤清单与建议，**不替编辑 / 平台做一票否决的最终决定**。
- **B8 不覆盖无关能力**：不处理与签约潜力无关的写作辅助（纯润色、查重、封面、发布等）。

## 5. 验收标准（必须可检验）

> 以下每条均可由 QA 通过「给定一本 NovelGo 小说 + 运行本工作流」并**经工具读取真实数据**来核对。

- **AC1（入口与阶段清单）**：触发后，技能输出明确的阶段清单（含①规划蓝图②世界/设定③写作推进④签约体检⑤闭环修复），每个阶段列明：目标、完成判据、建议调用的现有技能名（`story-blueprint` / `worldbuilding-design` / `signability-audit`）、以及题材卡约束提示。
- **AC2（状态感知，不重复触发）**：对同一本**已存在 story_arc** 的小说再次触发工作流，技能应经 `get_chapter_list` + 蓝图数据读取确认「规划阶段已完成」，**从写作/体检阶段开始引导**，而非重复规划。
- **AC3（规划阶段产物）**：完成规划阶段后，本书数据存在 `story-blueprint` 的落库痕迹——经 `create_story_arc` / `create_arc_node` 写入的 ≥1 条主线 arc + ≥1 个 arc_node，或经 `update_chapter_plan` 更新的卷纲；由 NovelGo 数据读取工具核实存在。
- **AC4（设定阶段产物，可选）**：若进入世界设定阶段，本书设定库出现 ≥1 条 `upsert_setting` / `create_location` 记录，可由数据读取工具核实。
- **AC5（体检阶段产物）**：完成体检阶段后，本书存在 `signability-audit` 写入的「本书签约体检」偏好（经 `upsert_preference`，类型为签约体检），包含七维打分、致命伤清单、P0/P1 建议；由偏好读取工具核实存在。
- **AC6（闭环修复）**：当体检报告含 ≥1 条 P0/P1 建议时，技能输出「回修指引」，明确把每条建议映射到「回到哪个阶段 + 调用哪个技能」；若用户执行，应能在对应阶段再次落库（新增/更新 arc 或 setting 或 plan，可由读取工具核实）。
- **AC7（题材卡约束遵守）**：工作流全程引导语出现对本书 `genreTemplates` 关键字段（如爽点密度 / 字数门槛 / 禁止漂移）的引用与提示；若本书无题材卡，技能提示「未配置题材卡，将按通用网文标准引导」且**不报错中断**。
- **AC8（不越权 / 不重写，结构校验）**：校验技能目录，本工作流技能正文不包含 `create_story_arc` / `upsert_setting` / `run_subagent` 等直接落库指令的复制；且 `story-blueprint` / `worldbuilding-design` / `signability-audit` 三个文件未被本技能修改（哈希/内容不变）。
- **AC9（空数据兜底）**：若本书无可达数据（`get_chapter_list` 返回空或读不到），技能提示「无法读取本书数据，请确认在 NovelGo 项目中」并停止，**不臆造任何产物**。

## 7. LLM / 脚本分工

**结论：本技能预期为「纯 LLM 提示词编排」（单文件 SKILL.md），不需要独立脚本。**

分工判据：

- **交给 LLM（提示词编排）的部分**：
  - 阶段定义、引导语、出口判据的撰写（自然语言）。
  - 运行时依据读取到的真实数据判断用户所处阶段（C3 状态感知）。
  - 把体检 P0/P1 建议映射到回修阶段与技能（C4）。
  - 题材卡约束的引用与提示（C5）。
  - 调用 `run_subagent` 做交叉验证的指令编排。
- **交给确定性代码 / 现有工具的部分**（均由被编排技能与其调用的 NovelGo 业务工具承担，本技能不重做）：
  - 落库：`create_story_arc` / `create_arc_node` / `update_chapter_plan` / `upsert_setting` / `create_location` / `create_location_relation` / `create_timeline_entry` / `create_reader_perspective_entry` / `upsert_preference`。
  - 读取：`get_chapter_list` / `read`（章节）。
  - 评分与交叉验证：`signability-audit` 七维打分、`run_subagent(review)`。

**为什么不需要独立脚本 / 不需要 `references/`**：
- 所有「硬逻辑」（落库、评分、写入设定库、交叉验证）已被 3 个被编排技能及其工具实现完毕。
- 编排层本质是自然语言的「阶段 + 调度 + 汇总」，**纯提示词即可表达**，且更利于 LLM 在运行时灵活依据真实数据决策。
- 单文件 `.md` 与 §6 的 `channel=local` / 独立技能交付物形态一致，降低维护与打包成本。
- `references/` 仅在阶段引导语过长需外置时才需要；本需求下正文内联即可，列为**非必需**。

**可选增强（非必需，列为待确认）**：若下游发现「阶段状态机需要**程序化可靠判定**（而非 LLM 自行判断）」或「需要对多次体检结果做 diff 对比」，再考虑引入一个轻量 `references/` 或脚本；当前需求下不必要。

## 8. 数据来源

> **铁律：禁止假设数据已存在。** 编排技能在一切阶段判定之前，必须**实际调用读取工具拿到真实结果**；读不到即按 AC9 兜底。

本技能运行依赖的本书数据及读取方式：

| 数据项 | 用途 | 读取工具 / 接口 | 状态 |
|--------|------|----------------|------|
| 章节列表 | 现状诊断、体检抽样 | `get_chapter_list` | ✅ 已知可用 |
| 章节正文 | 体检通读、规划参考 | `read`（读章节） | ✅ 已知可用 |
| 题材卡 `genreTemplates` | 全程约束遵循（C5） | 应用层注入 / 待确认主动读取工具 | ⚠️ 待确认 |
| 已有蓝图（arc / arc_node / chapter_plan） | 阶段判定（C3） | 待确认 `get_*` 类工具 | ⚠️ 能力缺口/待确认 |
| 已有设定库（setting / location） | 阶段判定（C3） | 待确认 `get_*` 类工具 | ⚠️ 能力缺口/待确认 |
| 已有「本书签约体检」偏好 | 阶段判定 / 闭环（C4） | 待确认偏好读取工具（现有仅 `upsert_preference` 写） | ⚠️ 能力缺口/待确认 |
| 读者/编辑视角条目 | 体检产物核验 | `create_reader_perspective_entry`（写已知，读待确认） | ⚠️ 读待确认 |

- **写入侧**工具（落库）在背景中已明确给出，且**不由本技能直接调用**（见 B2），由被编排技能调用。
- **读取侧**中，仅 `get_chapter_list` 与 `read` 在本背景中明确可用；其余「读取已有 arc / setting / preference」「读取题材卡」的接口**未在本背景中给出确切工具名**——NovelGo 应提供对应读接口（技能需可读可写才合理），但本需求说明书**不臆测确切名称**，统一列为 §10 的「能力缺口 / 待确认」。

## 9. 关键决策建议：新建 `signability-workflow` 还是演化 `next.md`？

**建议：新建独立技能 `signability-workflow`（中文名「签约潜力工作流」），不建议复用 / 演化 `next.md`。**

论证：
1. **职责不同**：`next.md` 原始意图是「引用蓝图 + 签约自检」，语义偏向「写下一章」的推进；本次要的是「规划 → 设定 → 写作 → 体检 → 修复」**端到端签约潜力编排**，「写下一章」只是「写作推进」子阶段之一，语义更宽、更偏规划与评估。
2. **模式冲突**：`next.md` 当前为 `mode=auto`（常驻可被 LLM 按需 `read`）；而引导式长工作流更适合 `mode=manual`（用户主动进入，避免每次聊天都加载长编排提示干扰其它技能）。复用会强制改动 `next.md` 的 mode 语义，牵连其原意图。
3. **命名清晰性**：`signability-workflow` 名自解释，降低用户在技能矩阵中的认知成本；`next.md` 保留给「下一章写作建议」场景，互不干扰。
4. **演进余地**：若未来要把 `next.md` 作为「写作推进」子阶段的可选调用目标，可在 `signability-workflow` 的「写作」阶段提示调用 `next.md`，而非合并。

> 结论：本需求交付物 = 新建 `signability-workflow`；`next.md` 保持原状（可作为写作阶段的可选子调用，不强制）。

## 10. 能力缺口 / 待确认

1. **读取已有蓝图/设定/偏好的 `get_*` 接口未明确**：用于阶段状态判定（C3）。需 NovelGo 侧确认提供对应读取工具（建议 `get_story_arcs` / `get_settings` / `get_preferences` 之类命名），否则 C3 的阶段感知无法可靠实现。
2. **题材卡 `genreTemplates` 读取方式未明确**：是应用层注入系统消息，还是需主动读取工具？需确认。
3. **「本书签约体检」偏好的读取接口未明确**：背景仅给 `upsert_preference`（写），闭环修复（C4）需要能读回历史体检。
4. **跨体检 diff（可选）**：暂无工具支持多次体检结果对比，若要做「修复前后对比」需新增能力，列为可选增强。
5. **三参数（§6）为假设**：platform=workbuddy / channel=local / deliverable=独立内置技能 `.md`，待用户确认。
6. **触发模式（§3）**：`mode=manual` 或 `auto` 为设计阶段决策，本需求推荐 manual + useWhen 收窄，未锁定。
