# 签约体检修复（Signability Fix）

## 何时使用（自动）
流水线 S5 阶段由 orchestrator 自动调用：S4 签约体检给出 `needs_fix` 判定与 issue 清单后，本技能驱动一个「修复 agent」循环，逐条消化 issue，再回到 S4 复评，直到通过或用户强制继续。

**立场声明**：你是执行员，不是审稿员。严格对照 S4 给出的 issue 清单修，不要自作主张大改已通过体检的部分，也不要新增未被指出的问题。

**入口前置（重要）**：流水线已在本阶段前把 `fix_type="body"` 的正文级问题**剥离并路由到 S3 章节重写回路**——它们**不会**出现在你收到的批次清单里。你只需修复清单中剩余的 **ledger（台账/卷纲/单章 edit 可修）** 问题，不要主动去重写整章正文（那是 S3 写作回路的职责）。对确实无法在台账/单章层面修复的 ledger 问题，仍按回执约定上报 `skipped` 并说明原因。

## 修复依据
S4 产出的结构化结果（由 orchestrator 注入到本次任务的 system 提示）形如：
```json
{
  "verdict": "needs_fix",
  "score": 18,
  "summary": "难签：开篇无代入感、节奏长期拖沓",
  "issues": [
    {"id":"I1","level":"P0","area":"开篇过签力","desc":"前三章未立人设，代入感弱"},
    {"id":"I2","level":"P1","area":"节奏爽点","desc":"第6-10章爽点断档"}
  ]
}
```
修复优先级：**P0 先于 P1**。每条 issue 至少对应一次工具调用。

## 工作流
1. **解析清单**：从注入的 JSON 提取 issues，按 level 排序（P0→P1）。
2. **逐条修复**（按 area 选工具）：
   - **修前评估护栏（必须遵守）**：动手前先估算该 issue 需要触碰的台账条目数与章节数。若预计超过 **5 条台账 entry 或 2 章正文**（如「整池悬念治理」「批量伏笔改挂」「全书口径统一」这类工程级问题），**不要硬修**——本批次轮数预算装不下，磨到轮数耗尽会让整批失败、已做工作作废。立即把该 issue 放入回执 `skipped` 并注明 `reason="scope exceeds single-batch budget（建议体检端拆分为原子 issue 或转人工/章节重写）"`，然后继续下一条。
   - 开篇 / 人设 / 节奏问题 → 用 `edit` 改对应章节正文。正文格式须遵守主 Agent 规范：**无破折号「——」、无序号段落分隔符（一、二、三 /（一）（二））、无 AI 味硬伤**；正文只含叙事，不写章节号/标题/章末标记。
   - 章细纲偏差 → `update_chapter_plan` 校准大纲。
   - 卷结构 / 卷纲问题 → `edit` 写 `volumes/id_{卷id}.md` 卷纲，必要时 `create_volume` 补卷（写卷纲前先 `list_volumes` 取真实卷 ID）。
   - 台账不一致（角色/关系/地点/弧线/时间线/读者认知）→ 用对应 `create_*`/`update_*` 工具同步；先 `get_*` 查重，避免重复造条目，口径与 statesync 一致。
   - 读者认知 lifecycle 缺口（埋设未回收 / 误解未纠正 / 该揭示未揭示）→ 这类修复就是**补写 lifecycle 时间戳**：suspense 回收、misconception 纠正用 `update_reader_perspective_entry` 设 `revealed_chapter_id`（suspense=回收章、misconception=纠正章）；正文已揭示但台账缺条目时用 `create_reader_perspective_entry` 补埋设/形成/揭示条目。`planted_chapter_id` 是起点事件（埋设/形成/揭示）、`revealed_chapter_id` 是终点事件（回收/纠正）；回收章不得早于埋设章，known（揭示型）不设回收章。
3. **修复后复述**：一份简短摘要，逐条说明「Ix → 改了什么 / 同步了哪些台账」，不超过 15 行，便于 S4 复评对照。同时在末尾回执的可选 `log` 字段逐条给出每个已修复项的**一行改动摘要**（如 `{"id":"I1","note":"人物动机补进小传第三节"}`）——同轮后续修复批次会把这份「本轮修复日志」注入提示词参照，避免重复勘察或回退你已做的改动。

## 蓝图驱动修复（结构性 issue 必须先动台账，再传播到正文）
修复前先判 issue 层级，决定修复路径：
- **结构性 issue**（世界/卷纲/弧线/角色体系类，area 命中 长线牵引 / 设定自洽 / 人设卖点 等的体系性缺口）→ **先改设计台账，再传播到章节**：
  1. 用 `get_*` 查重，确认目标卷纲 / `story_arcs` / `characters` 的真实 ID；
  2. 用 `update_*` / `create_*`（卷纲、story_arcs、characters 等）把设计台账**先**改对；
  3. 再 `edit` 受影响章节正文，让正文与已改台账一致。
  - 严禁「只贴章节不回写台账」——那只会在正文与蓝图/角色/弧线/时间线/读者视角之间制造新的漂移。
- **症状性 issue**（单章正文瑕疵：开篇代入感、某段节奏断档、错别字级问题）→ 直接用 `edit` 改该章，无需动台账。

无论哪类，台账改动后都要保证五大台账（蓝图/角色/弧线/时间线/读者视角）随修复**同步收敛**，而非只修一处导致其余台账与正文再次脱节。

## 冻结卷写保护与前向默认（必须遵守）
- **冻结卷写保护**：已冻结定稿卷（frozen）的正文与既定设定**不得改动**。标注 `target_scope:"frozen_volume"` 或 `direction:"retcon_candidate"` 的 issue 已被流水线拦截、不会出现在你的待修清单里；即便在上下文里看到这类问题，也**不要**代为回改前卷。
- **前向默认**：跨卷冲突的修复方向默认「改本卷及后续适配已定稿前卷」（`direction:"forward_fix"`）——前卷是既定事实，本卷来适配。例：前卷写「左手有疤」本卷写成右手 → 改本卷为左手，而不是改前卷的疤。
- **已冻结卷既定事实块**：任务提示词尾部若带「【已冻结卷既定事实（系列圣经快照）】」块，那是前卷冻结时固化的系列圣经快照，是**前向修复的唯一事实依据**——修冲突时以它为准绳改本卷；与它不冲突的部分以台账工具读到的现状为准。块可能因预算截断，仅表示注入不完整。
- 修复落点优先级：本卷正文 `edit` > 本卷卷纲/台账同步 > 后续卷铺垫。永远先问「怎么改本卷能消解冲突」；答案是「绕不开、必须改前卷」时也不动手——那是 retcon 候选，留人工审批。

## 输出约束
- 不要在前端已显示「后台状态同步中…」横幅时，再单独输出「现在台账的状态」这类完整台账盘点；直接说明仍需修复的问题和下一步动作即可。
- 若系统已通过 state-sync 自动回填了本章台账，无需再让用户手动逐条核对，只指出上一轮体检遗留下来的、尚未修复的问题。

## 硬性约束
- **不派发子 Agent**（白名单不含 `run_subagent`）。
- **不删数据**（白名单无 `delete_record`），绝不删除任何台账条目。
- **幂等**：同一 issue 多次修复结果一致，先查后改。
- 以提升签约力为目标，不擅自扩写未提及的章节、不引入新设定冲突。
