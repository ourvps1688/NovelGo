# 流水线核心重构提案：从「阶段闸门 × 批量全书审计」到「章节 CI × 稀疏深审 × 作用域修复」

> 状态：提案（探讨产物，未排期、未动工）。§10 为第二轮探讨定案（检测核心化：拿掉自动修复、检测环节独立启动、G 闸门降级为汇总视图）。
> 前置文档：`ultimate-form-integration-plan.md`（P0–P4 已全销）；本提案针对 P0–P4 **刻意未触碰**的继承基座——S0–S6 编排内核（源自 `volume-scoped-pipeline-implementation-wbs.md` 阶段 0–4）。
> 纪律承袭：一任务一提交、宁缺勿错、降级逐字一致、P0–P2 工件零触碰、度量纯本地、只报告不拦截、theme token、desktop-first。

## 0. 结论（TL;DR）

流水线**存在根本性设计问题，但不是全盘皆错**。

- **根本问题的根**：质量控制是**离线批处理**——用"全书逐章通读的 LLM 审计"当质量信号源，用"串行小批独立会话"当修复手段，用"每轮全量复评"当验收手段。三者叠加使成本随书长超线性膨胀、问题发现滞后数章、修复闭环被乘法放大（体感"修复闭环特别慢"即此症）。
- **不是根问题的部分**：确定性状态机（Orchestrator.Advance 唯一裁决点）、issue 契约单源、冻结快照/写保护/retcon 状态机、P0 装配器 / P1 Voice / P2 确定性漂移检测 / P4 熔断重试——这些是**健康资产，新方案在其上加层而非推翻**。
- **新方案一句话**：把质检从"定期全书批审"改成"每章增量 CI"（确定性 L0 + 小上下文 L1）+ 稀疏深度体检 L2（黄金三章/卷收口/完本）；把修复从"串行小批独立会话"改成"issue 工单化 + 作用域分组并行 + 增量复验"；把执行体从"裸 goroutine + JSON 状态袋"改成"持久任务队列"。
- **全书质量覆盖（§8 补强，回应"是否足够"）**：仅靠 §4 不足以覆盖"全书级矛盾/修改错误/一致性"——需补三个组件：**长程结构索引层**（伏笔/悬念/人物状态机/时间线约束/节奏曲线，全书问题从档案序列做确定性推理而非重读正文）、**台账可信度与对账**（provenance + 正文↔台账双向对账，防错误固化）、**修复传播检查**（依赖图定向复验下游章节，防改一处破他处）。补强后方案才够格称"全书质量方案"。
- **本质定位（§9 校准）**：本引擎是**长篇网文写作引擎**，质量的唯一定义是**签约级 + 追读**（商业可验证），不是泛文学性。质量主要**规划出来**（章纲/坑表/节奏曲线），检查层只是兜底；检查信号、检查时机、确定性规则全部按网文实际写作（黄金三章、章尾钩子、爽点密度、挖坑填坑、战力体系、去 AI 味、日更节奏、发布不可逆）重校准。

## 2. 结构性诊断（根本问题，代码证据）

### F1 · 全书 LLM 审计是质量信号主源：成本 O(书长)，里程碑重复触发使全生命周期 O(n²)

- 体检提示词要求「**逐章通读全部已成稿章节**（黄金三章逐字精读，其余分批评完，**不得抽样跳章**）」（`service.go:2334`；存量体检 :2075、终检 :1840 同款措辞）。
- 但轮数预算恒定 24 轮，注释自认矛盾：「长篇动辄 70+ 章，12 轮在长篇上会在读完全书前耗尽……放宽到 24 轮」（:862-864）。**"不得抽样"与"轮数上限"在长篇上互斥**——成本照付，保证却静默降级为浅读。
- 触发节奏：黄金三章首检 + **每 5 章里程碑复检**（`orchestrator.go:150-152`，`store.go:71-73`）+ 卷边界 + 每轮修复后复评 + 完本终检。第 10/15/20… 章各做一次全量通读 → 全书生命周期内正文被重复审读的总次数约 **n²/10** 量级。
- 卷级 scoped 定界（`delegateVolumeAudit`）把范围缩到"当前卷"，缓解了全书面，但**卷内仍是逐章通读且每 5 章重复**，问题本质未变。

### F2 · 修复闭环乘法放大（"修复特别慢"的直接出处）

- 切批过细：`fixBatchP0=1`（P0 整章改写级独占）、`fixBatchP1=2`（:1022-1023）→ N 个问题切出大量小批次；
- **串行** for 循环逐批执行，且**每批一个独立 agent 会话**（`SessionID: "pipeline:"+runID+":fix:"+uuid`，:1311 附近；注释明说为防历史消息挤占轮数预算）→ 零上下文共享，每批重读台账/正文；
- 每轮修复完成后 `finishFixAndReaudit` → **全量复评**（一次完整 LLM 体检，24 轮）；仍 needs_fix 则再来一轮，最多 `autoFixCap=3` 轮；body 级再进重写回路最多 `autoRewriteCap=2` 轮（每章 18 轮独立会话）。
- 修复技能契约（`signability-fix.md`）要求每条 issue ≥1 次工具调用、结构性 issue "查重→update/create→edit" 多步传播、预计超预算的"工程级问题"直接 skipped——**被 skip 的问题每轮复评都会重现**，再吃一轮 24 轮全量复评，空转。
- 粗算最坏路径：3 轮 ×（多批 × 18 + 全量复评 24 + 巡检 8）+ 2 轮整章重写 × 18 ≈ **数百 LLM turn**，其中真正改稿的 turn 占少数，读与复评占大头。

### F3 · 发现滞后：问题引入点与修复点分离（shift-right）

- 一个在第 3 章引入的设定矛盾，最早在黄金三章体检（第 3 章）或下个里程碑（第 5/10 章）被发现，此时后续章节已在其上叠加构建 → 修复要么回改第 3 章引发连锁适配（retcon 压力），要么接受前向妥协。
- 章级"写后质检"存在（`next.md` 阶段 3：identity 清单 + deai 复核 + `run_subagent(review)`），但它是 **LLM 在同一会话内的自检自觉**（自评偏差 + 靠技能文案"不通过不准进下一章"约束，无机制强制），与流水线的独立体检是两套节奏、两套信任等级。

### F4 · 编排状态字符串化倾倒 + 裸 goroutine 执行体

- `GateContext` 20+ 字段全部序列化塞进 `PipelineRun.ContextJSON` 字符串（`store.go:58-131`）：体检结果、修复断点、重写积压、retcon 候选、轮数计数、中断标记、派发标记……每次读改都是整体 unmarshal/marshal，防御性守卫随处可见（"若异步执行期间用户已推进……不覆盖新状态"，`service.go:911-918`）。
- 执行体是 fire-and-forget goroutine（`go s.executeAudit` :809、`go s.executeFix` :830），进程重启即消亡 → 靠 `Interrupted`/`Dispatching` 两个 JSON 布尔 + `RecoverInterruptedRuns`/`redispatchIfNeeded`（:2460/:2514）打补丁式自愈。
- 已有真实补丁史佐证复杂度在积累：FixStates 与复评 issue 的 ID 撞车（LLM 惯性编号 I1..In）会把全部问题误判"已修复"空转到上限——为此专门加了清零逻辑（:900-903 注释完整记录了这个 bug 的形态）。**每加一个行为 = 一个 JSON 字段 + 一类守卫**，是复杂度利滚利，不是设计收敛。

### F5 · LLM 文本输出直接驱动控制流

- 章号从 issue 的 `area/desc` **正则解析**（`parseChapterRefs`，:2260）来定位重写目标；修复回执从回复文本解析（`parseFixReceipt`，:2129）；体检结论从文本抽取（`parseAudit`，:2153）。
- 为此需要整套防御：issue JSON 契约单源 + 契约测试（`contract.go`）、schema_version 版本门、字段嗅探陈旧判定（`auditStaleReason`）。这些防御工程本身是好的，但它们的存在证明了根因：**把 LLM 当成了可靠事件源**。事实层的裁决（改哪章、修没修、动不动冻结卷）本应由确定性代码依据结构化字段做，LLM 只提建议。

### F6 · 双编排器并存，节奏靠约定对齐

- `next.md`（LLM 自调度的每章四阶段：写前对齐→写中代入→写后质检→周期体检）与 Go 状态机（Orchestrator.Advance，S0–S6 + G 闸门）**并行存在**：阶段 3 写后质检 ≈ 章级 review，阶段 4 周期体检（"每 5~10 章手动触发 signability-audit"）≈ 里程碑 S4。两套节奏没有机制性互斥/互锁，只靠技能文案约定不撞车。

## 4. 新方案：章节 CI × 稀疏深审 × 作用域修复

### 4.0 核心理念转变

```
现状：写 → (每 5 章) 全书批审 → 串行小批修 → 全量复评 → ……   （离线批处理，O(n²)）
终态：写 → 每章 CI(L0 确定性 + L1 小上下文) → 作用域修(并行) → 增量复验
         ↘ 稀疏 L2 深审（黄金三章 / 卷收口 / 完本）做汇总裁决            （在线增量，O(n)）
```

质量信号从"少数几次昂贵的全书 LLM 通读"换成"每章廉价的增量检查沉淀成档案，深审只做汇总裁决"。

### 4.1 核心概念一：章节质量档案（Quality Ledger）

每章落盘后（statesync 旁路）沉淀一份结构化质检档案：L0 指标全集、L1 issue 清单、修复状态、影响的台账条目。它是章节的"体检病历"，落独立表（勿塞 GateContext）。

**L2 深审的输入从"全书正文"改为"各章档案汇总 + 关键章深读"**：黄金三章逐字精读、转折/卷末章深读、其余按档案抽样。LLM 从"阅读器"变"裁决人"。

### 4.2 核心概念二：三级检查金字塔（chapter CI）

| 层 | 内容 | 成本 | 频率 | 信任与处置 |
|---|---|---|---|---|
| **L0 确定性** | 字数/结构门槛、P2 文风八键漂移（复用 `style.ComputeStats` vs `voice.MetricKey`）、台账引用存在性（章内实体均可在台账找到）、时间线顺序、与冻结快照的既定事实规则比对、章尾钩子存在性 | 毫秒级，零 LLM | 每章必跑 | 事实性问题，**可直接进修复路由**（结构化、无歧义） |
| **L1 增量 LLM** | 只读「本章 + 前章结尾/次章开头 + 涉及台账条目 + 本章计划卡」，查一致性/连贯/读者认知态/伏笔 lifecycle | 小上下文（对比全书通读降 1~2 个量级） | 每章一次 | warning 级起步；issue 进档案，**同会话或紧邻会话趁热修** |
| **L2 深度体检** | 现行 8 维签约体检，但输入改为档案汇总 + 关键章深读 | 高 | 黄金三章、卷收口、完本终检；里程碑降为"档案汇总快审" | 裁决 verdict，进 G 闸门 |

关键点：
- **里程碑体检不再逐章通读**（F1 根治）：改成档案汇总 + 抽样深读，成本 O(1)~O(抽样) 而非 O(书长)。
- L1 初期严格沿用 P2 纪律：**只报告不改写、warning 级、零 issue 零提示**；误报率经使用数据（本地度量）验证后再升 gate。
- L1 每章固定增加一次小上下文 LLM 调用——比"每 5 章全书通读"的摊薄成本低得多，且换来发现滞后从 5 章缩到 1 章。

### 4.3 核心概念三：修复即工单（fix as work items）

1. **issue 一等公民化**：落独立表（stable key、`chapter_ids []int64` 结构化字段【替代 `parseChapterRefs` 正则，F5 根治】、fix_type、target_scope、dimension、direction、status、round）。契约单源 `contract.go` 直接演化为该表 schema（契约测试继续强制同步）。
2. **作用域分组并行**：issue 按 `chapter_ids`/台账条目求交集分组——**组间并行派发，组内串行**（写冲突天然规避）；取代"P0=1/P1=2 串行小批"（F2 根治）。
3. **修复日志共享**：同轮各会话注入「本轮修复日志」（已修条目摘要 + 台账 diff），消除独立会话的重复勘察（F2）。
4. **增量复验**：修复后只对**修过作用域**做 L1 级针对性复验；全量复评仅存于 L2 深审（卷收口/完本）。
   - 权衡明示：增量复验可能漏"连带影响"——兜底是卷收口的 L2 全量深审 + L0 规则扫描全书，与"宁缺勿错"的取舍点在此并接受之。
5. **被 skip 的"工程级问题"立即转人工工单**，不再每轮复评重现空转（F2 尾部根治）。

### 4.4 核心概念四：持久任务队列 + 瘦状态机

- 执行体（L1 检查、修复会话、L2 深审、重写）从裸 goroutine 迁到 **task 表**（kind/payload/status/attempt/lease/heartbeat）：幂等消费、崩溃续跑、可并行、可观察（前端可见队列进度——与 P3 旅程面板天然契合）。
- `GateContext` 瘦身为**纯决策记录**（gates 历史 + 各结论的表引用），大对象（Audit/RewriteBacklog/RetconBacklog）独立表化。Interrupted/Dispatching 两个补丁布尔随 goroutine 时代一起退役。
- `Orchestrator.Advance` **原样保留**为唯一"下一步去哪"裁决点；变化仅在"执行体怎么派发"（`go executeX` → 入队）。

### 4.5 双编排器合一

`next.md` 收缩为**纯写作技法编排**（写前对齐 + 写中技法）；其"阶段 3 写后质检 / 阶段 4 周期体检"由机器化 chapter CI 承担（不依赖 LLM 自觉），技能文案中的强制语删除，避免两套节奏（F6 根治）。

| **R3 任务队列化** | 执行体迁 task 表；GateContext 瘦身；Interrupted/Dispatching 退役 | F4 | 中高：触及恢复路径，需迁移集成测试 |

依赖与纪律：
- R0–R4 全程 **P0–P2 工件（contextasm/voice/snapshot/retcon）零触碰**——新层只在其外围消费数据。
- 所有新检查遵守降级逐字一致（失败=零提示零报错）、只报告不拦截（warning 先行）、度量纯本地。
- 每阶段一个提交、过验收再进下一阶段；真实 LLM E2E 瞬态按既定纪律复跑收口。

## 8. 全书质量覆盖评估与补强（回应"是否足够"）

> 问题：目标是解决**全书的质量问题、矛盾、修改错误、全书一致性**——§4 的设计是否足够？
> 答案：**对"越写越对"的增量一致性足够且强于现状；对"全书级/长程"问题有三个真实缺口，必须补强。**其中一个缺口正是 §4.2 为省成本主动削弱的（L2 从逐章通读改为抽样），不能回避。

### 8.1 问题分类 × 覆盖对照

| 问题类别 | 典型例子 | §4 原设计覆盖 | 缺口 |
|---|---|---|---|
| 局部/相邻章一致性 | 前章说黑后章说白、称谓漂移 | ✅ L1 增量窗口 + L0 文风八键 | — |
| 事实矛盾（规则可判） | 死人复活、时间线倒错、吃书 | ⚠️ 台账比对可查**已入账**事实 | **台账漏记/记错即漏检**（G2） |
| 事实矛盾（语义级） | 角色动机与前文行为冲突、承诺违背 | ⚠️ L1 单章窗口看不到远距前文 | **跨章语义矛盾**（G1） |
| 全书涌现属性 | 伏笔烂尾、悬念断档、多章拖沓、弧线残缺、多线失衡 | ❌ L2"汇总+抽样"恰好比现状全书通读**更弱** | **G1 主体** |
| 修改错误（修复副作用） | 改第 3 章破坏第 20 章前提 | ⚠️ 增量复验只看修过作用域 | **下游传播**（G3） |
| 主观文学质量 | 文笔、情绪、爽点成败 | ⚠️ 留给 L2/人工 | 有意保留人工裁决，非缺口 |

### 8.2 补强组件 A：长程结构索引层（治 G1）

全书级问题**大多不需要重读正文**——它们在"每章档案 + 结构表"的序列上是可推理的。新增（多为台账既有四维的**生命周期扩展**，机制复用）：

| 结构表 | 检查（确定性或近确定性） |
|---|---|
| **伏笔 lifecycle 表**（埋/收状态 + 埋设章/预期收章） | 埋超 N 章未收 = 烂尾告警；收未埋 = 无源告警（现有 `get_story_arcs`/`search_story_memory` 有雏形，补状态机） |
| **悬念池 / 钩子表** | 连续 N 章悬念无净增减 = 断档；章尾钩子缺失（L0 已列）聚合为"钩子密度曲线" |
| **人物状态机**（生死/在场/关系/认知） | 死人出镜、关系倒错——**规则可判的矛盾直接 L0 拦截**，不依赖 LLM |
| **时间线全局约束** | 并行事件可满足性求解（不止顺序）；跨章时距矛盾 |
| **节奏曲线**（爽点密度/情绪值/信息增量，L1 逐章产出） | 连续 N 章低值 = 拖沓，**从档案序列直接看出，零重读** |
| **用户书写不变量（pinned invariants）** | 作者声明的硬约束（"主角第 X 章前不死""力量体系上限 Y"）→ L0 每章必检；直接服务"矛盾/错误"，且能拦住任何自动检查都想不到的写作错误 |

LLM 在此层的角色：**对结构索引做汇总裁决**（读表不读全书），只对告警点做**定向深读验证**（读被告警的 2~3 章原文确认真伪）。

### 8.3 补强组件 B：台账可信度与对账（治 G2）

台账是全书比对的基准，**基准错了下游全错**（statesync 提取错误会被固化为"事实"）：

1. **provenance**：事实条目带来源章节 + 提取置信/人工确认标记；核心事实（角色生死、重大设定、读者真相 reveal）可**钉住**（人工确认后任何自动修改需走 retcon 级审批）。
2. **双向对账巡检**：定期"正文 ↔ 台账"对账（`consistency-patrol` 思路加强）：正文与台账冲突时**不预设谁对**——可能改正文（现行方向），也可能是**台账记错该修台账**（S5 的 `fix_type=ledger` 已有此出口，方向判断补进 L1 契约）。
3. **台账变更留痕**：修台账本身进修复日志（§4.3-3），复验时同步核对台账修改的下游影响。

### 8.4 补强组件 C：修复传播检查（治 G3）

修复/重写的副作用靠**依赖图**定向复验，不做全量复评也不裸奔：

- 依赖边来自台账：章节 ch 引用台账条目 X → 所有引用 X 的章节是 ch 的**下游依赖**；伏笔/时间线/人物状态表同理。
- 改动章节后：取依赖闭包（通常 2~5 章）做定向 L1 复验 + L0 全书规则扫描兜底；
- 依赖闭包超阈值（如 >8 章）说明该问题是**结构性牵连**，直接升级走 L2 深审/人工，不硬修。

### 8.5 L2 深审重定位

原 §4.2 的 L2"档案汇总 + 抽样"重定位为三层输入：**结构索引（8.2）全量 + 质量档案全序列 + 关键章定向深读**；抽样深读只负责验证，不负责发现。全书逐章通读不删除，而是降频为**卷收口/完本/用户主动**的"编辑部通读"（低频高价，主观裁决 + 涌现属性终审）。

### 8.6 认知边界（诚实声明）

机器层的目标是把**硬伤类问题**（矛盾/错误/不一致/烂尾/副作用）的检出率与修复闭环做到系统性、可持续；主观文学判断（这样写好不好）的最终裁决留给人工与低频全书通读。补强 A+B+C 后，本方案对"全书质量"的覆盖从"约 60%（且长程更弱）"提升到"硬伤类接近全覆盖、主观类有裁决通道"——这是与现状（LLM 全书批审：贵、慢、长篇上浅读且无结构沉淀）相比的质变点：**现状每做一次全书体检都从零读起，新方案的全书视图是常驻资产**。

## 9. 从网络小说实际写作出发的校准（质量模型重校准）

> 前提定锚：本引擎是**长篇网文写作引擎**，产出目标是**签约级**（平台编辑视角可过签、读者视角可追读）。一切设计从网文连载的实际出发，不做泛文学创作系统的抽象。

### 9.0 三条纲领

1. **质量的定义 = 签约 + 追读**。可验证信号：过签（黄金三章留存、8 维签约体检）、追读（章尾钩子强度、爽点密度、节奏曲线、坑的埋收节奏）。不是"写得美不美"，是"读者弃不弃、编辑收不收"。
2. **质量是规划出来的，检查只是兜底**。AI 写长篇的头号失败模式不是单章写砸，而是**写着写着漂移/烂尾/同质化**——根源在规划层（大纲/卷纲/章纲/坑表）失控。引擎的重心放在"每章为什么写、写什么"（章纲任务卡），检查层负责拦截硬伤与预警掉追读风险。
3. **发布不可逆，写前把关 > 写后修复**。VIP 章发出即定稿，回头大改=口碑事故。检查与修复尽量前移到**章纲级**（此时改动成本最低），正文级只兜残余。

### 9.1 对齐网文写作金字塔（检查点前移）

```
大纲/蓝图 ── L2 蓝图体检（已有 blueprint-audit，长线不烂尾的前提）
   │
卷 纲 ────── 卷收口 L2 + G_freeze 冻结（已有；卷纲与坑表对齐检查）
   │
章 纲 ────── 【新增·章纲检查】章纲 vs 坑表/人设/战力表/节奏曲线 冲突检查（L1.5）
   │            ← 写前把关的核心新增层：便宜一个量级、可随意改
正 文 ────── L0 确定性 + L1 增量（§4.2；每章任务卡驱动生成）
   │
发布前 ────── 钩子/爽点/去 AI 味 checklist（L0 指标 + L1 复核），分钟级不阻塞日更
   │
数据回流 ──── 质量档案 + 追读代理指标（本地）→ 校准检查器权重（§9.4）
```

生成侧的每章输入（章纲任务卡，`next.md`"本章功能卡"的机制化）必须含四件套：**钩子任务**（本章埋/收哪个坑、章尾断章钩子设计）、**爽点任务**（情绪曲线落点）、**人设时刻**（谁的高光/反差）、**推进任务**（主线/卷纲功能位）。生成 agent 按卡产出，L1 按卡验收——"本章为什么写"从技能文案约定升为机器可验契约。

### 9.2 网文特有崩点 → 确定性检查器（L0 扩充，零 LLM）

网文老书虫抓的虫高度集中，大多**规则可判**：

| 崩点 | 检查器 | 依据 |
|---|---|---|
| **战力/境界崩坏**（网文第一崩点） | 境界等级表 + 战力对照表数值化；"越级胜利无代价""低阶碾压高阶"规则拦截 | 力量体系台账扩展（worldbuilding 已有设定条目，补数值序） |
| **吃书**（设定前后矛盾） | 设定规则条目（金手指边界/世界规则）钉住为不变量，逐章比对 | §8.2 pinned invariants |
| **称呼/人名漂移** | 别名/称呼表（正名/昵称/职务/自称），称呼混用告警 | characters 台账扩展 |
| **死人出镜/时间线倒错** | 人物状态机 + 时间线约束求解 | §8.2 组件 A |
| **坑烂尾/无源** | 伏笔 lifecycle（埋/收/预期收章），超期未收告警 | §8.2 组件 A |
| **章尾无钩/断章失败** | 章尾结构规则 + L1 钩子强度评分（题材卡参数化） | 题材卡「章尾钩子」约定 |
| **爽点断档/节奏拖沓** | 节奏曲线（逐章爽点/情绪值入档案），连续 N 章低值告警 | 题材卡「爽点密度/情绪曲线」参数化 |
| **AI 味** | P2 文风八键指纹（句式/比喻密度/破折号/套话词表）确定性扫描 | deai-flavor 的确定性部分 |

**题材卡从文案约定变成机器可检参数**：爽点密度下限、章尾钩子类型、禁忌清单（禁虐主/破墙/吃书等）都进检查器配置——"题材卡优先级最高"由机制保证而非技能自觉。

### 9.3 节奏与场景约束

- **日更级时延**：正文落盘 → L0/L1 出结果的目标时延分钟级；任何检查不得阻塞"每天 2 章"的连载节奏（异步任务队列天然满足，结果进质量档案随时可看）。
- **开篇预算倾斜**：黄金三章是签约生死线——前 3 章逐字精读 + 反复打磨式修复（修复预算向其倾斜，值得多轮）；前 30~50 章（上架追读线）做加密抽检；中后段靠档案+抽样。**深审资源不均匀分布，这是符合商业现实的取舍。**
- **长线不烂尾的节奏锚**：卷纲级预埋"卷末爆点/卷钩"，坑表带预期收章（大致区间）；引擎在规划期就报"这个坑 30 章内无收点""本卷无爆点位"——比写完再发现便宜得多。

### 9.4 数据回流与校准（度量红线内）

- 质量档案的追读代理指标（钩子强度/爽点密度/弃读风险告警数）纯本地统计；未来可支持**用户主动导入**真实阅读数据（追读/订阅曲线）做校准——告警权重按"与掉追读的相关性"调整（仍本地计算，不上传）。
- L1/L2 的告警→真问题命中率进本地度量（P4 底座）：误报率高的检查器降权，命中率高的升 gate。检查体系自身也迭代，不靠拍脑袋定阈值。

### 9.5 与 §4/§8 的关系

§4 解决"闭环又贵又慢"（工程骨架），§8 解决"全书级覆盖"（长程结构），§9 解决"质量定义与检查信号对不对"（产品灵魂）。三者合成完整的网文写作引擎质量体系：**规划层产出质量（章纲/坑表/曲线）→ 生成层按卡成文 → 检查层拦硬伤预警掉追读 → 修复层按作用域快修 → 数据层校准一切**。

## 10. 第二轮定案：检测核心化（拿掉自动修复、环节独立启动、G 闸门降级）

> 探讨触发（2026-01）：「目前的流水线设计还是有问题，我想拿掉自动修复这个环节，流水线的每一个环节都可以单独进入和启动，流水线核心做检测的工作。」
> 本节是**方向定案**（四个关键分叉已拍板），覆盖/修订 §4.3 与 §5 的部分内容。R0–R4 仍按原计划有效；R5 在其后收口。

### 10.1 方向定案（已拍板）

| 分叉 | 定案 |
|---|---|
| 创作流 S0–S3 去留 | **保留，降级为编排预设**——仍是完整产品能力，但只是"写→检测"的便捷串行壳；检测环节可脱离它独立启动 |
| 人工修复入口形态 | **发现项工单面板 + 按钮触发**（去修复 / 复验 / 驳回），每步可视可审计 |
| G 闸门（G1/G1b/G3b/G4/G终） | **降级为检测汇总视图**——不再阻塞流程，是否推进由人决定 |
| 落地节奏 | **先落本文档再动手**（即本节），按 R5 迁移路线实施 |

### 10.2 核心定位转变：流水线核心做检测

流水线核心的交付物收敛为两样，**不再产出"修复完成"类结论**：

1. **质量档案**（chapter_quality，逐章累积的客观检测结果）；
2. **发现项工单**（需要人看一眼的东西：issue 台账升格，状态机 `发现 → 确认 →（人工）修复中 → 复验通过/驳回`）。

界面话语随之诚实化：只说「检测完毕，发现 N 项」，不再有「自动重写完成」。R2b 的结构索引层/巡检/章节 CI 本来就是纯检测零写入，与本定位天然一致——本节把它们从"流水线的附属检查"升格为**产品主语**。

### 10.3 拿掉自动修复（S5 自动重写回路退役）

- **删除**：`rewriteLoop` 自动重写回路、复评自动回流、`autoRewriteCap` 轮数上限、finishFixHandoffRewrite 自动派发、rewrite_handoff 自动交接，及全部"自动重写完成"类文案。F2 的复杂度（烧 RewriteRounds、谎报完成、熔断落地语义）随回路整体消失——它们是被回路逼出来的补丁，回路没了即无根。
- **转换**：RewriteBacklog / 复评发现 → **发现项工单**。修复动作永远由人显式触发（一次一章/一批皆可），修复完成后**显式点"复验"**回到检测环节（复验沿用 §4.3-4 增量复验逻辑，只是不再自动串起来）。
- **保留**：修复执行能力本身（定向重写/edit、作用域分组、修复日志共享），全部改为**被动响应工单**。

### 10.4 环节独立启动：从线性 run 到按 scope 启动的检测任务

- **检测任务统一形态**：章节 CI、卷体检、书体检、巡检·结构都是同一类"检测任务"——各有独立入口、独立 scope（某章/某卷/全书/全书结构）、任意时刻可单独启动，不依赖流水线走到哪一步。章节 CI 已是该形态原型，推广之。
- **全书流水线降级为编排预设**：只是"写→检测"按序串起的便捷壳。可以只跑检测不跑流水线，也可以只跑流水线不手动跑检测。"从第 N 章续写""只体检第 X 卷""只查伏笔"都是一等公民操作。
- 执行体仍走 R3 任务队列（检测任务是队列的一类 kind），事件协议/前端旅程面板不变。

### 10.5 G 闸门降级为检测汇总视图

G1/G1b/G3b/G4/G终 不再是硬性串行关卡，变为**本阶段检测结论一览**（汇总质量档案 + 未决工单 + verdict），是否推进由人决定。Orchestrator.Advance 仍是"下一步去哪"的唯一裁决点，但裁决默认交还用户；`volume-scoped-pipeline-implementation-wbs.md` 的闸门语义（冻结/retcon 边界）不变，只是不再自动卡流程。

### 10.5b 签约体检的地位澄清（第二轮讨论补充）

**签约体检没有丢，是检测核心的质量裁决主角**——它是 §9 质量定义（签约级+追读）的直接载体。被拿掉的只是缠在外面的两条自动耦合（体检→自动修复、体检→闸门硬卡），体检本体四要素去向：

| 要素 | 现状 | 新方案 | 改动量 |
|---|---|---|---|
| 触发 | 流水线自动（黄金三章/每 5 章/卷边界） | 检测任务自动节奏 + 随时手动（见下） | 节奏保留，入口扩充 |
| 输入 | 三层输入（结构索引+质量档案+关键章深读） | 原样保留 | **零改动** |
| 产出 | 8 维 verdict + issue 清单 | 8 维 verdict + 发现项工单 | 换容器，内容不变 |
| 消费 | G 闸门硬卡 + 自动进 S5 修复 | 汇总视图建议 + 人工修复按钮 | 硬卡→建议，自动→人工 |

组件级对照：S4 体检本体 → 检测任务「书体检/卷体检」（signability-audit.md 契约/三层输入/goldenN 逻辑零改动）；S4b 里程碑体检 → 已落 R2-4 档案汇总快审；S6 完本终检 → 书体检 scope=final；存量全量体检 → 书体检手动入口（升一等公民）。

**触发策略定案（已拍板）：保留自动检测节奏 + 手动入口**——"检测全自动、修复全人工"，与"核心做检测"完全一致：

- **自动**：写后章节 CI（不变）；黄金三章首检、每 5 章快审、卷收口、完本终检在**编排预设内自动触发**对应检测任务（可跳过，结果进质量档案+工单，不阻塞）；
- **手动**：任何检测任务（章节/卷/书/巡检·结构）任意时刻可单独启动——自动是节奏保障，手动是一等公民入口；
- **人工**：修复永远由工单按钮显式触发，显式复验。

风险红线：**不得把自动触发节奏改成纯手动**——纯手动下没人点按钮 = 签约体检事实性消失。自动节奏是它存活的机制保障。

### 10.7 R5 迁移路线（每步独立可交付、独立可回退）

| 步骤 | 内容 | 风险 |

| **R5-1 工单化** | 发现项工单表（issue 台账升格：状态机 + 复验回执）+ 工单面板（去修复/复验/驳回按钮）；RewriteBacklog 读写改走工单 | 中：契约兼容读 |

```
创作人驱动：写（S0–S3 预设或单章）→ 检测任务（章节 CI / 卷体检 / 书体检 / 巡检，可任意单独启动）

```
